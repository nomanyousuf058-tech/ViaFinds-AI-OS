## 3. Affiliate Link System

### Current implementation
- **Creation**: Affiliate URLs are generated by the automation pipeline at `lib/automation/pipeline.ts:1811` — `affiliateDecision.affiliateUrl || null` is written directly to `articles.affiliate_url`.
- **Storage**: Stored as `TEXT` in `articles.affiliate_url` and `products.affiliate_url`. Also in `affiliate_references` table (polymorphic, `content_type` + `content_id`).
- **Redirects**: NONE. Affiliate links go directly to the partner network (e.g., `https://www.digistore24.com/redir/112312/1727525`).
- **Tracking**: NONE. No intermediate redirect layer, no sub-ID injection, no click recording.
- **Product association**: Via `affiliate_url` string only — no `product_id` FK on articles.
- **Article association**: Via `articles.affiliate_url` column.
- **CTA association**: The CTA block in article content has `url` but no `cta_id` or tracking.

### Can ViaFinds answer "Which article generated this affiliate click?"

**NO.** There is no click tracking infrastructure. Affiliate links are direct URLs to partner networks with no redirect or tracking layer. The `affiliate_references` table stores URLs but does not track clicks.

### What is missing
1. A redirect/tracking link handler (e.g., `/go/[shortcode]` that 302s to the real affiliate URL)
2. Sub-ID injection into affiliate URLs (e.g., `?subid=article_X_cta_1`)
3. Unique affiliate link ID per CTA
4. Database table for `affiliate_links` with article/product/CTA association

## 5. Conversion Tracking

### Does conversion tracking exist?
**NO.** There is no conversion tracking, webhook ingestion, or order data retrieval.

### Evidence
- **Database**: No `conversions`, `orders`, `sales`, `transactions` table exists.
- **API**: No `/api/webhook*`, `/api/conversion*`, or `/api/order*` endpoints exist.
- **Digistore24Provider** (`providers/affiliate/Digistore24Provider.ts:146`): Only has `discoverProducts()` and `testConnection()`. NO method for retrieving order/conversion data. NO webhook handler.

- **Digistore24 API key**: NOT configured (confirmed in `scripts/generate_audit_report.ts:85` and `.env.example`).

### Realistic alternatives
Since Digistore24 does NOT have API keys configured and has NO revenue reporting integration:
1. **Digistore24 API**: Configure the API key and use Digistore24's `listOrders` or reporting API to retrieve sales data correlated by Sub-ID.
2. **Digistore24 Webhooks**: Digistore24 supports postback/webhook notifications — implement receiving endpoints.
3. **Manual import**: Download CSV/XLS reports from Digistore24 dashboard and import.

Currently NONE of these are implemented.

## 12. Revenue Attribution Model

### Minimum Practical Attribution Model

```sql
-- 1. affiliate_links: Unique tracked affiliate links
CREATE TABLE affiliate_links (
  id UUID PRIMARY KEY,
  article_id UUID REFERENCES articles(id),
  product_id UUID REFERENCES products(id),
  opportunity_id UUID REFERENCES brain_opportunities(id),
  cta_id VARCHAR(100),          -- for multi-CTA articles
  destination_url TEXT NOT NULL,   -- the real partner URL
  sub_id VARCHAR(255),            -- injected into affiliate URL (?subid=...)
  short_code VARCHAR(50) UNIQUE,  -- for /go/[short_code] redirect
  created_at TIMESTAMPTZ
);

-- 2. affiliate_clicks: Track every click through the redirect
CREATE TABLE affiliate_clicks (
  id UUID PRIMARY KEY,
  affiliate_link_id UUID REFERENCES affiliate_links(id),
  article_id UUID REFERENCES articles(id),
  ip_address INET,
  user_agent TEXT,
  referrer TEXT,
  clicked_at TIMESTAMPTZ,
  session_id VARCHAR(100)
);

-- 3. affiliate_conversions: Record conversions from partner API/webhooks
CREATE TABLE affiliate_conversions (
  id UUID PRIMARY KEY,
  affiliate_link_id UUID REFERENCES affiliate_links(id),
  article_id UUID REFERENCES articles(id),
  product_id UUID REFERENCES products(id),
  click_id UUID REFERENCES affiliate_clicks(id),
  sub_id VARCHAR(255),
  amount DECIMAL(10,2),
  currency VARCHAR(10),
  commission DECIMAL(10,2),
  status VARCHAR(50),
  partner VARCHAR(50),
  converted_at TIMESTAMPTZ
);

-- 4. article_revenue: Daily rollups per article
CREATE TABLE article_revenue (
  article_id UUID REFERENCES articles(id),
  date DATE,
  clicks INTEGER,
  conversions INTEGER,
  commission_usd DECIMAL(12,2),
  revenue_usd DECIMAL(12,2),
  PRIMARY KEY (article_id, date)
);
```

This model answers all the required questions with minimal tables.

- **HIGH**: The in-memory `jobs` object is loaded once at module init. If multiple server instances run (e.g., Vercel), each has its own in-memory copy. Writes to `jobs.json` are NOT atomic — concurrent writes race.
- **Vercel serverless**: Each request is a new serverless function instance → the in-memory cache is lost between invocations → only `jobs.json` file is the shared state.

### Persistence risks
- **HIGH**: JSON file on local filesystem. On Vercel serverless or container deploys, this directory is ephemeral. Jobs can be lost on redeployment.
- **No backup**: JSON file is not included in Supabase backups.

### Deployment risks on Vercel
- **HIGH**: Vercel serverless functions have read-only filesystem (except `/tmp`). The `data/automation/jobs.json` path is NOT in `/tmp`, so writes will fail on Vercel production deploys.
- The code currently works on local/VPS deployments but will silently lose jobs on Vercel.

### PostgreSQL equivalent already exists
- `automation_jobs` table exists in schema (see `lib/db/schema.sql:252-278`)
- `lib/db/repositories/automation-jobs.ts` provides full CRUD for the table
- `automationJobsRepository.create()` is called in `app/api/brain/tasks/[id]/execute/route.ts:102`
- BUT: The actual JobManager (`lib/automation/job-manager.ts`) does NOT use this repository. It uses JSON files.
- There is a **split-brain problem**: the API route creates a DB record, but the pipeline creates a JSON file record. These are never reconciled.

### Migration complexity
- **MEDIUM**: Requires rewriting `JobManager` methods (`createJob`, `getJob`, `updateJobStatus`, `setJobResult`, etc.) to use PostgreSQL instead of `fs`.
- The PostgreSQL `automation_jobs` table already has compatible schema (UUID id, idempotency_key, status, stage, input JSONB, result JSONB, audit_log JSONB, retry_count, etc.).
- The JSON-based job IDs (`job_${Date.now()}_${random}`) would need to change to UUIDs to match the DB schema.
- BrainTaskWorker references `job.id` — would need to ensure compatibility.

### Recommendation
**MIGRATE** the JobManager to use PostgreSQL. The infrastructure exists; it needs to be wired up. This should happen alongside click/conversion tracking since both require new database tables.
